# AeroEquip — 大型商用运输类飞机设备管理数字化平台

> 产品设计规格文档 (Product Design Specification)
> 版本: 1.0 | 日期: 2026-04-20

---

## 1. 产品定位

### 1.1 目标市场

面向**飞机主制造商**（如商飞、波音、空客等）的**设计/总体部门**，服务飞机研制阶段的设备选型、安装设计和构型管理。

### 1.2 核心价值主张

当前主制造商的设备管理数据散落在 CATIA（几何模型）、PLM（BOM 结构）、Excel（重量/电负荷/DO-160）等多个系统中，缺乏以"设备"为中心的统一管理界面，加改装评审靠人工核算约束，安装位置管理靠 2D 图纸和脑补。

AeroEquip 提供：

1. **统一视图** — 以设备为锚点，整合分散在多系统中的全维度技术数据
2. **约束实时校验** — 设备加改装时自动计算重量/CG/电负荷/空间冲突等约束并预警
3. **空间可视化** — 2D/3D 直观浏览设备安装位置、EWIS 线缆路径和空间关系

### 1.3 竞争壁垒

**航空领域专业深度 + 可视化体验差异化**，定位为"飞机设备管理垂直领域专家系统"。

- 与通用 PLM（Teamcenter/3DExperience）的区别：PLM 做通用产品数据管理，AeroEquip 把 ATA/DO-160/MEL/EWIS/电负荷等航空专业逻辑全部内置，开箱即用
- 与传统 Excel 管理方式的区别：数据关联、实时约束校验、空间可视化、流程协同

### 1.4 产品范围

- **型号支持**：产品线级 — 支持多型号、同型号多系列（基本型/加长型/公务型）、多构型版本
- **部署模式**：私有化部署优先，架构预留混合云扩展能力
- **集成策略**：标准 API + 文件导入（Excel/CATIA）为主，架构预留 PLM 双向集成和 CATIA 插件接口
- **用户范围**：全链条覆盖 — 工程师、专业工程师、评审专家、供应商、管理层

## 2. 系统架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│                     用户接入层 (Web Frontend)                  │
│  工程师工作台 | 空间可视化中心 | 约束校验中心                    │
│  评审协同中心 | 供应商门户     | 管理看板                       │
├─────────────────────────────────────────────────────────────┤
│                     统一 API 网关 (REST + WebSocket)           │
├─────────────────────────────────────────────────────────────┤
│  核心域: 设备台账 | 构型管理 | 型号/系列 | 用户/RBAC | 审计日志  │
├─────────────────────────────────────────────────────────────┤
│  领域专业层: 重量CG | 电负荷 | EWIS | DO-160 | 安装布局 | 可靠性 │
├─────────────────────────────────────────────────────────────┤
│  协同流程层: 变更评审 | 供应商协同 | 文档生成 | 通知 | 报表导出   │
├─────────────────────────────────────────────────────────────┤
│  数据层: PostgreSQL | MinIO | Meilisearch | Redis             │
├─────────────────────────────────────────────────────────────┤
│  集成层: CATIA导入 | PLM同步 | Excel导入 | 开放API              │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 分层职责

| 层级 | 职责 | 技术 |
|------|------|------|
| 用户接入层 | 6 个功能中心，面向不同角色提供专属工作界面 | React + TypeScript + Ant Design |
| API 网关 | 统一认证、路由、限流。WebSocket 支持约束结果实时推送 | FastAPI + WebSocket |
| 核心域 | 设备台账（全系统数据锚点）、构型版本管理、型号/系列层级、RBAC 权限、操作审计 | FastAPI + SQLAlchemy + Alembic |
| 领域专业层 | 6 大专业域的计算引擎和业务规则，每个引擎独立可调用 | Python + NumPy |
| 协同流程层 | 加改装评审流程引擎、供应商填报/审核、文档自动生成、消息通知 | Celery + Redis |
| 数据层 | 关系型主库 + 对象存储 + 全文检索 + 缓存 | PostgreSQL + MinIO + Meilisearch + Redis |
| 集成层 | 外部系统数据导入/同步适配器 | openpyxl + CAD Exchanger SDK |

### 2.3 设计原则

- **对外是一个产品**：统一体验、统一定价、统一交付
- **对内分层解耦**：各层独立演进，开发可并行，升级不连锁
- **设备是全局锚点**：所有领域数据以设备为外键关联
- **元数据驱动**：ATA 结构、区域定义、母线配置、评审模板均为可配置数据，新型号上线无需改代码

## 3. 功能模块

### 3.1 六大功能中心

#### ① 工程师工作台

**主要角色**：设备管理工程师、总体工程师

**核心能力**：
- 设备台账 CRUD（件号/名称/ATA/重量/功耗/坐标/供应商）
- 设备选型对比（同类设备参数横向比较）
- 加改装方案编制（选设备 → 定位置 → 配母线 → 校验约束 → 提交评审）
- 构型快照管理（创建/锁定/回滚基线版本）
- 批量导入导出（Excel / CATIA 数据）
- **实时约束面板**（内联在右侧，操作即反馈）：
  - CG 位置 + 包线状态
  - 各母线负荷率 + 余量
  - 近 5 次构型变更趋势
  - 操作预演（勾选设备后预览全约束影响）

#### ② 空间可视化中心

**主要角色**：总布置工程师、EWIS 工程师；所有角色可只读访问

**核心能力**：
- **2D 三视图**（默认模式）：侧视图 / 俯视图 / 截面图（沿 STA 可选），SVG 渲染
- **3D 整机模型**（按需加载）：半透明机身壳体 + 设备实体色块 + 剖切面交互
- **EWIS 线缆路径**：Three.js TubeGeometry 渲染线束，选中信号后高亮完整路径
- **空间冲突检测**：设备间距校验 + 维修通道可达性评估
- **区域(Zone)着色**：不同 Zone 用不同底色，叠加设备密度
- **设备定位联动**：从任何列表点击设备 → 视图自动飞到对应位置（300ms 动画）

#### ③ 约束校验中心

**主要角色**：重量工程师、电气工程师、适航工程师、EWIS 工程师

**核心能力**：
- **重量/CG**：实时计算全机重量和重心位置，CG 包线图可视化，超限告警
- **电气负荷**：各母线设备功耗汇总，飞行阶段工况切换（正常/应急/最大），余量分析
- **DO-160 环境鉴定**：安装位置 → 环境分区映射 → 鉴定类别匹配 → 合规校验，缺项清单
- **EWIS 分离校验**：电源/信号/感烟线缆分离距离校验，防护等级检查
- **MEL/CDL 影响评估**：设备失效对最低设备清单的影响分析，放行限制建议
- **「假设分析」**：模拟加/减设备后的全约束影响预览，不实际修改数据，< 300ms 返回

#### ④ 评审协同中心

**主要角色**：评审专家、项目经理、总师/副总师

**核心能力**：
- 加改装方案评审流程（发起 → 专家审签 → 会签 → 批准）
- 变更影响分析报告自动生成（附全维度约束前后对比）
- 评审意见跟踪与闭环管理
- 多方案对比决策支持（A 方案 vs B 方案全维度对比）
- 电子签章 / 审批链配置
- 并行会签（多位专家同时签署，无需串行等待）

#### ⑤ 供应商门户

**主要角色**：设备供应商（受限权限）

**核心能力**：
- 设备技术参数填报（重量/功耗/尺寸/接口/DO-160 证书）— 结构化表单
- 技术文档上传（ICD/安装手册/维修手册）
- 设备状态更新（停产通知/替代件推荐/ECN 变更通知）
- 消息通知（参数需确认/文档需更新）
- **权限隔离**：仅可见自己供应的设备，无法查看整机构型、其他设备或约束结果

#### ⑥ 管理看板

**主要角色**：部门领导、项目经理、质量管理

**核心能力**：
- 型号级设备统计仪表盘（总数/ATA 分类/区域分布/新增趋势）
- 约束健康度总览（全机各约束维度的裕度一览，红黄绿状态）
- 评审进度跟踪（待审/进行中/已完成/超期统计）
- 供应商绩效（响应时效/文档完整率/停产风险设备数）
- 多型号横向对比（产品线级统计）

### 3.2 六大领域专业引擎

| 引擎 | 输入 | 计算逻辑 | 输出 |
|------|------|---------|------|
| 重量与CG | 每台设备: mass(kg) + arm(STA/BL/WL) | 重量累加 → 力矩计算 → CG%MAC → 包线校验 | 当前CG位置、各限重余量、✓/✗包线内 |
| 电气负荷 | 每台设备: power(kVA) + bus + flight_phase | 各母线按飞行阶段累加 → 与额定容量比较 | 各母线负荷率%、余量kVA、>85%告警 |
| EWIS | 线束路径(3D点序列) + 线缆类型 + 防护区域 | 路径间距计算 → 分离规则匹配 → 防护等级检查 | 分离违规清单、防护缺失提示、路径长度/重量 |
| 环境鉴定 | 设备安装区域 + 区域环境定义 + 鉴定证书 | 位置→环境分区映射 → DO-160类别匹配 | ✓鉴定覆盖/✗缺项清单/等级差异报告 |
| 安装布局 | 设备尺寸 + 安装坐标 + 机身结构边界 | 3D包围盒碰撞检测 → 间距校验 → 通道可达性 | 冲突对列表、间距不足告警、可维修性评分 |
| 可靠性 | MTBF + 装机数量 + 使用剖面 + 供应商状态 | MTBF加权 → 系统可用度 → 备件预测 → 停产预警 | 系统可用度、年故障预测、备件量建议 |

### 3.3 横切功能

| 功能 | 描述 |
|------|------|
| 全局搜索 | 按件号/名称/ATA/区域/供应商模糊搜索，结果直达设备详情或空间定位 |
| 构型对比(Diff) | 任意两个构型版本的差异对比：新增/移除/变更 + 约束影响汇总。Git diff 心智模型（红删绿加橙改） |
| 文档自动生成 | 装机设备清单 / 重量报告 / 电负荷表 / 变更影响报告 / DO-160鉴定矩阵 / MEL影响评估。输出 PDF + Excel + Word |
| 智能预警 | 约束临界→黄灯；超限→红灯阻断；供应商停产→替代件推荐 |
| 操作审计 | 所有数据变更记录 who/when/what/why，支持回溯和合规审查。双层审计：ChangeRequest（业务级）+ AuditLog（字段级） |
| 数据权限 | 按型号/项目/角色三维控制数据可见性，支持密级标识和脱敏导出 |

## 4. 数据模型

### 4.1 实体关系概览

```
Program (型号)
  └── Series (系列)
        └── Configuration (构型版本)
              └── M:N ──── Equipment (设备，核心锚点)
                              ├── Installation (安装位置: STA/WL/BL/Zone/Rack)
                              ├── WeightBalance (重量: mass/arm/cg)
                              ├── ElectricalLoad (电气: bus/kva/phase/mode)
                              ├── EWISInfo (布线: connector/pins/wires/separation)
                              ├── DO160Qualification (鉴定: categories/cert/env)
                              ├── Reliability (可靠性: mtbf/mttr/failure_rate/spares)
                              ├── N:1 → Supplier (供应商)
                              └── 1:N → Document (技术文档)

Zone (区域定义, 按 Series 可配置)
BusDefinition (母线定义, 按 Series 可配置)
ChangeRequest (变更请求) → ReviewFlow (评审流程)
AuditLog (审计日志)
```

### 4.2 设计原则

| 原则 | 说明 |
|------|------|
| 设备是锚点 | 所有领域数据以 Equipment.id 为外键关联，一个设备 = 一份完整技术画像 |
| 构型是快照 | Configuration 与 Equipment 为 M:N（通过关联表）。同一设备可存在于多版本构型。基线锁定后不可修改 |
| 三级层次 | Program → Series → Configuration。Zone/Bus 等基础定义在 Series 级别，不同系列可有不同区域划分 |
| 领域数据拆表 | 6 个领域属性各为独立子表，不塞大宽表。原因：(1)不同设备可能只有部分领域数据 (2)各领域独立演进 (3)供应商只填自己负责的字段 |
| 变更可追溯 | ChangeRequest 记录业务级变更上下文，AuditLog 记录字段级变更。两层审计 |
| 元数据驱动 | ATA 章节树、环境分区、母线配置、评审模板均为可配置数据，新型号上线无需改代码 |

### 4.3 核心实体字段

#### Equipment（设备 — 核心实体）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | 主键 |
| part_number | VARCHAR | 件号（唯一标识） |
| name | VARCHAR | 设备名称 |
| ata_chapter | VARCHAR | ATA 章节（如 "34-21"） |
| equipment_type | ENUM | 类型：LRU / SRU / 结构件 / 线缆 |
| manufacturer_id | FK → Supplier | 供应商 |
| status | ENUM | 在研 / 鉴定中 / 已批准 / 停产 |
| description | TEXT | 设备描述 |
| created_at | TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | 更新时间 |

#### Configuration（构型版本）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | 主键 |
| series_id | FK → Series | 所属系列 |
| version | VARCHAR | 版本号（如 "V2.3"） |
| status | ENUM | draft / baseline / frozen / archived |
| created_by | FK → User | 创建者 |
| locked_at | TIMESTAMP | 基线锁定时间（null = 未锁定） |
| description | TEXT | 版本说明 |

#### ChangeRequest（变更请求）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | 主键 |
| config_id | FK → Configuration | 目标构型 |
| title | VARCHAR | 变更标题 |
| description | TEXT | 变更背景和理由 |
| equipment_adds | JSONB | 新增设备列表 |
| equipment_dels | JSONB | 移除设备列表 |
| equipment_mods | JSONB | 变更设备列表（字段差异） |
| impact_summary | JSONB | 约束影响汇总（6 大引擎校验结果快照） |
| status | ENUM | draft / validating / reviewing / approved / rejected / withdrawn |
| submitted_by | FK → User | 提交人 |
| approved_at | TIMESTAMP | 批准时间 |

## 5. 核心工作流

### 5.1 加改装评审流程

```
① 发起需求 → ② 编制方案 → ③ 约束校验 → ④ 专家会签 → ⑤ 总师批准 → ⑥ 纳入基线
```

**流程规则**：

| 规则 | 说明 |
|------|------|
| 草稿阶段 | 方案可反复修改，约束校验可随时手动触发预览。不进入正式流程 |
| 校验阻断 | 硬性超限（CG 出包线 / 母线过载）时，系统阻止提交评审。必须先修改方案 |
| 告警放行 | 软性告警（接近限值 / 非关键项缺失）时，允许提交但需填写风险说明 |
| 并行会签 | 多位专家可并行签署意见，系统显示会签进度和剩余待签人 |
| 基线纳入 | 批准后自动：(1) 创建新构型版本 (2) 锁定为基线 (3) 生成交付文档 (4) 通知相关方 |

### 5.2 实时约束校验流程

**触发方式**：任何设备操作（添加/移除/修改参数/移动位置/切换母线）

**执行流程**：
1. 前端发送变更指令到后端 API
2. 后端基于当前构型 + 本次变更，并行调用 6 大引擎计算
3. 汇总结果为 ValidationReport，通过 WebSocket 推送前端
4. 前端实时更新约束面板

**校验结果状态**：

| 状态 | 含义 | 交互行为 |
|------|------|---------|
| ✓ PASS | 所有引擎通过 | 绿灯，可正常操作 |
| ⚠️ WARNING | 有软性告警 | 黄灯，可继续但提交评审需说明 |
| ✗ BLOCKED | 有硬性超限 | 红灯，阻止提交，必须修改 |

**性能要求**：
- 单设备变更校验：< 500ms
- 100 台设备批量导入后全量重算：< 5s
- 2000 台设备完整构型全量校验：< 10s
- 假设分析预览：< 300ms

### 5.3 供应商协同流程

**主制造商侧**：创建设备条目 → 指定供应商 → 系统发送填报邀请 → 审核供应商数据 → 确认纳入/退回修改

**供应商侧**：收到邀请 → 登录门户 → 填写结构化表单 → 上传文档 → 提交审核

**权限隔离**：供应商仅可见自己负责的设备条目，无法查看整机构型、其他设备、区域信息或约束计算结果。数据脱敏 + 接口限制双重保障。

### 5.4 文档自动生成

| 文档 | 内容 | 格式 |
|------|------|------|
| 装机设备清单 | 按 ATA/区域分组的完整设备列表 + 关键参数 | PDF / Excel |
| 重量平衡报告 | 全机重量汇总 + CG 计算过程 + 包线图 + 裕度 | PDF / Excel |
| 电负荷分析报告 | 各母线负荷明细 + 飞行阶段工况 + 余量 | PDF / Excel |
| 变更影响分析报告 | 涉及设备 + 全维度约束前后对比 + 风险评估 | PDF / Word |
| 环境鉴定矩阵 | 设备 × DO-160 试验项覆盖矩阵 + 缺项清单 | PDF / Excel |
| MEL 影响评估 | 设备失效对 MEL 影响 + 放行限制建议 | PDF / Word |

## 6. 可视化设计

### 6.1 设计原则

基于"视觉四人组 + 马斯克"的共识：

- **默认 2D**：80% 场景用 SVG 三视图解决，轻量高效
- **3D 按需加载**：仅 EWIS 路径追踪和空间冲突检测时需要 3D
- **内联反馈**：约束结果嵌入操作界面右侧，不跳页
- **数字+进度条+趋势线**：核心状态用最简洁的方式呈现
- **构型对比用 diff 模式**：红删绿加橙改，程序员熟悉的心智模型
- **安静界面**：正常时绿色小圆点安静存在，异常时红色脉冲抢注意力

## 7. 技术栈

| 层级 | 技术 | 选型理由 |
|------|------|---------|
| 前端框架 | React 18+ / TypeScript | 生态最大，企业级组件库丰富，TS 保障可维护性 |
| UI 组件库 | Ant Design 5.x | 国内企业级标准，表格/表单/流程组件完整 |
| 2D 可视化 | SVG (React 原生) + D3 辅助计算 | D3 只做坐标变换和布局算法，不做 DOM 操作 |
| 3D 可视化 | Three.js + React Three Fiber | 懒加载，R3F 让 3D 与 React 状态管理无缝集成 |
| 后端框架 | Python / FastAPI | 异步高性能，自动 OpenAPI 文档，NumPy 做约束计算 |
| 实时通信 | WebSocket (FastAPI native) | 约束结果实时推送，协同状态同步 |
| 任务队列 | Celery + Redis | 批量导入、全量校验、文档生成异步执行 |
| 主数据库 | PostgreSQL 15+ | JSONB 灵活扩展、物化视图、RLS 行级安全 |
| 搜索引擎 | Meilisearch | 轻量全文搜索，中文分词，单二进制部署 |
| 对象存储 | MinIO (S3 兼容) | 3D 模型/文档存储，私有化友好，未来可迁公有云 |
| 容器化 | Docker + Docker Compose | 一键部署全套服务，客户环境只需 Docker |
| 编排(可选) | Kubernetes | 大规模/高可用场景，中小规模 Compose 足够 |
| 文件解析 | openpyxl + CAD Exchanger SDK | Excel 导入导出 + CATIA 文件解析/glTF 转换 |

## 8. 部署与运维

### 8.1 私有化部署架构

```
客户内网
├── Nginx (反向代理 + SSL + 静态资源)
├── Frontend (React SPA)
├── Backend (FastAPI × N 实例)
├── PostgreSQL (主数据库)
├── Redis (缓存 + 消息队列)
├── Celery Worker (异步任务)
├── MinIO (对象存储)
└── Meilisearch (全文检索)
```

### 8.2 环境要求

| 项目 | 最低配置 |
|------|---------|
| CPU | 8 核 |
| 内存 | 32 GB |
| 存储 | 500 GB SSD |
| 操作系统 | CentOS 7+ / Ubuntu 20.04+ / 麒麟 V10 / 统信 UOS |
| 浏览器 | Chrome 90+ / Edge 90+ / 国产信创浏览器 |

### 8.3 交付方式

- **安装包**：Docker 镜像 tar 包 + 部署脚本，全程内网运行，无外网依赖
- **升级**：增量镜像包 + 数据库迁移脚本（Alembic）
- **备份**：一键导出 PostgreSQL dump + MinIO 数据

### 8.4 信创兼容

- 支持国产 CPU（ARM64 / 龙芯）— Docker 多架构构建
- 支持国产 OS（麒麟 / 统信 UOS）
- PostgreSQL 可替换为国产数据库（达梦 / 人大金仓）— SQLAlchemy 方言适配
