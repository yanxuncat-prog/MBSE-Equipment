## 一、在线协同编辑

### 1.1 核心痛点 ✅
- 不再通过邮件/共享文档轮次收发，所有人在平台上直接编辑自己负责的字段
- 今天改了什么、明天改了什么，所有人实时可见
- 类似外网 WPS 云文档的协作体验，但带权限控制

### 1.2 数据组织原则 📌
- 90% 以上的数据以**设备清单为单元**去加属性、做看板、做统计
- 只有 EICD 和布置里面会有设备清单以外的东西（主体和模型）

## 二、构型管理

### 2.1 三构型并存对比 ✅
- 0号机（有人首飞）、X号机、1&2号机三个构型同时管理
- 首页看板**第一位置**显示：各构型设备总数（数如果不对，原数据就全不对）
- 构型对比：增/删/变更设备

### 2.2 0号机冻结基线 ✅
- 0号机有人飞的设备清单是冻结版本，一般不会改
- 令号和图号全部完整
- 任何人不可修改
- X号机和1&2号机以0号机为基准做 delta 对比

> 🔧 **澄清**：0号机冻结范围 = 令号、DM号、设备名称三个基本属性永久锁定。布置位置归布置专业管，跟随专业基线时间点冻结，不属于永久锁定范围。专业数据字段（重量、电负载、环境等）各专业独立设基线时间点，基线前自由编辑（有日志），基线后需审批。

### 2.3 设备唯一标识 ✅
- 0号机：可用令号做唯一标识
- X号机和1&2号机：令号不可靠（有两位数字要改为"00"），先用**设备名称**匹配，后续用**设备名称+令号**组合
- 同一令号在不同构型中可能对应不同设备（如"5G ATG CPE" vs "5G CPE"）
- DM号不能做唯一标识（一个DM号可能对应10个设备）

> 🔧 **澄清**：建立**设备库（EquipmentMaster）**，以件号（part_number）作为全局唯一标识。各构型中的设备通过外键关联到设备库中的唯一件号。件号采用**精确匹配**，不做模糊匹配。允许构型中的设备名称与设备库中的标准名称不一致。三个构型各自导入后，系统自动按件号匹配到设备库（件号完全一致才关联）。

### 2.4 设备名称不一致问题 ✅
- 同一设备在不同构型中可能叫不同名字
- 电推进电池有"A构型动力电池""B构型"等命名差异
- 需要开发方在后台处理匹配逻辑

> 🔧 **澄清**：通过设备库件号关联解决，不需要名称模糊匹配。只要两个构型中的设备关联到同一个设备库件号，就认定为同一种设备，即使名称不同。

## 三、重量专业

### 3.1 实测重量 vs 重量指标 ✅
- 每个设备展示：实测重量、总体分配的重量指标、差额（灯号量）
- 这是当前**最关心**的内容

### 3.2 减重信息（最优先展示）✅
- 0号机实测重量
- 1&2号机减重后重量
- 单设备减重量
- 全机累计减重量
- "减重的信息会更需要放在前面"——看板最优先位置

> 🔧 **澄清**：
> - 减重量 = 自动差值计算（0号机重量 − 1&2号机同件号设备重量），不需要维护单独的减重目标字段
> - 减重看板三个维度展示：设备本体减重、托架减重、合计减重
> - 展示位置：管理看板首页放摘要数字（全机累计减重） + 重量分析页放详细分析（按设备明细）

### 3.3 底层数据字段 ✅
- 重量（实测，含托架，湿重，单位 kg）
- 重心坐标（X/Y/Z，全机坐标系，单位 mm）
- 惯量（6 分量：Ix、Iy、Iz、Ixy、Ixz、Iyz，单位 kg·m²）
- 重量指标（由 PACE 提取）
- 超重风险

### 3.4 动态更新机制 ✅
- 设备可能换构型（今天A构型明天A+1构型），重量重心都会变
- 该系统章节的负责人重新填写数据
- 自动反映到全机重量重心看板上

### 3.5 数据来源 ✅
- 应从发布数模导出（理想状态），当前数模信息不全
- 重心数据当前可用，惯量大部分为空
- 惯量需要各系统负责人手动填写

> 🔧 **澄清**：重量指标有 PACE 导出文件可批量导入，需拿到样本文件确认解析格式。

### 3.6 重量指标冻结 ✅
- 0号机在某些卡大节点后，重量指标不能随便改
- "那个之前也随便改，那个之后动了之后就不能随便改"

### 3.7 设备托架重量数据不一致 ✅
- 设备清单里有重量，托架信息表里也有重量，两者可能不一致
- 处理规则：优先以重量表为准，重量表没有的才用托架表
- 后续需要整合两个来源的数据

> 🔧 **澄清**：设备重量（mass_kg）和托架重量（bracket_mass_kg）是两个独立字段，需分开展示，不是互相 fallback 的关系。合计重量由系统自动计算。

## 五、布置/MICD 专业

### 5.1 MICD 管控字段 ✅
不集成完整 MICD 报告文件（太复杂，那就变成 CDDS 平台了），只做字段管控：
- 安装结构件编号
- 电搭接面
- 紧固件牌号、数量、归属团队
- 设备托架型号
- 托架来源（自制/外购）
- 托架重量（bracket_mass_kg）
- 螺钉规格
- 线搭接接口尺寸
- 数模采用构型
- 是否包含公差尺寸工程图（支持上传图片附件）

> 🔧 **澄清**：MICD 是独立实体，与设备为一对多关系（一台设备可能有多条 MICD 记录，如同一设备不同安装位置）。具体字段类型待布置专业提供列头定义后确认。

### 5.2 MICD 确认状态 ✅
- 是否已签字确认 MICD
- 能统计出"去年我干了多少 MICD 确认工作"——工作量报表

### 5.3 布置协调 ⚠️ → 🔧 已澄清
- 希望布置协调的工作能在平台上体现一部分
- ~~具体形式未定~~

> 🔧 **澄清**：采用设备间约束关系模型——标记"设备A和设备B有安装位置依赖"（M:N关系），在调整布置时提醒关联影响。

### 5.4 布置位置严格管控 ✅
- "布置位置不可能是他想调哪调哪，是我们定哪是哪"
- 布置位置**不给任何下面的人编辑权限**，只有总体有权限

> 🔧 **澄清**：布置位置归布置专业管控，跟随专业基线时间点冻结，不属于构型基本属性的永久锁定范围。

### 5.5 不需要 2D 轻量化数模展示 ✅
- "那个不行，我其实不需要这些东西"
- 不要当前的轻量化数模，想要的是 MICD 信息管控

## 六、环境综合

### 6.1 DO-160 鉴定展示 ✅
- 设计等级（A1/B2）→ 鉴定状态（符合/不符合/待确认）的映射展示
- 按 ATA 筛选

> 🔧 **澄清**：DO-160 是独立实体，与设备为一对多关系。需覆盖 DO-160 标准的约 25 个测试类别（温度、振动、湿度、高度、电磁干扰等），每台设备每个类别一条记录。25 类测试类别为系统内置固定枚举。

## 七、实物管理（采购进度扩展）

### 7.1 完整实物管控流程 ✅
不止是采购，是一整套实物就位检查流程：
1. 设备采购状态：生产 → 测试 → 运输 → 到货
2. 预计到货日期、实际到货日期
3. 接口文件（MICD）是否已签署确认
4. 实物是否已开口（结构准备完成）
5. 设备是否达到安装要求
6. 全部检查项通过 → 达到装机要求 → 可以上机
7. 计划上机日期
8. 实际上机

> 🔧 **澄清**：每台构型设备独立跟踪这 8 个步骤，与设备为一对一关系。

### 7.2 看板形态 ✅
- 类似项目进度管理看板
- 不限于采购进度，包含实物状态全链路

## 八、权限管理

### 8.1 专业维度权限 ✅
- 重量人只改重量行、环境人只改环境行
- 各专业只编辑自己的字段，其他专业字段只读

### 8.2 ATA 维度权限 ✅
- 航电系统的人不能改环控系统的数据
- 每个用户绑定负责的 ATA 章节列表

### 8.3 构型基本属性锁定 ✅
- 令号、DM号、设备名称：**任何下面的人不可修改**
- 只有总体有权限
- "令号什么的前序那几个属性，已经不止加审批的事儿了，那个应该是不给他们编辑权限"

> 🔧 **澄清**：永久锁定属性为令号、DM号、设备名称三项。布置位置不属于永久锁定范围，归布置专业基线管控。

### 8.4 两阶段权限模型 ✅
参照 EICD 的做法：
- **阶段一（初期）**：无审批，快速填充空数据，变更有日志记录，通知到对应专业负责人
- **阶段二（打基线后）**：加审批流程，变更需总体专业负责人点"通过"，数据才变为有效

> 🔧 **澄清**：实施节奏——先搭轻量账号框架（登录 + 角色标识 + 操作日志记录"谁改的"），不实现审批流和字段级锁定。等核心数据管理功能稳定后再加审批流。

### 8.5 每个专业有自己的基线时间点 ✅
- "我重量不动了，但环境那队还测着呢，我肯定给不了数据"
- 每个维度（专业方向）有自己的基线冻结时间

### 8.6 分字段粒度管控 ✅
- 不是按整个专业打基线，而是按字段
- 某些字段已稳定 → 加审批
- 某些字段还在填充 → 不加审批
- 令号等基本属性 → 直接锁定不给编辑权限

### 8.7 角色定义 ✅
- PMO：只管人员权限分配，不编辑数据
- 系统集成：管所有数据权限
- 构型管理员：管设备增/删和基本属性
- 专业负责人：管本专业字段，可给下属授权
- 专业人员：编辑本专业字段
- 只读用户：仅查看

## 九、变更管理/日志/通知

### 9.1 变更日志 ✅
- 所有编辑操作必须有日志：谁在什么时间改了什么字段、从什么值改成什么值

## 附录 A：数据模型澄清（头脑风暴结论）

### A.1 设备库（EquipmentMaster）— 新增主数据表

```
EquipmentMaster
├── part_number (PK, 全局唯一件号)
├── master_name (标准名称)
└── 通用属性...

ConfigEquipment (构型设备)
├── id (PK)
├── master_part_number (FK → EquipmentMaster)
├── config_name (构型中的名称，可与 master_name 不同)
├── config_id (FK → 所属构型)
└── 构型特有属性...
```

### A.2 MICD 记录 — 一对多关系

```
MICDRecord
├── id (PK)
├── equipment_id (FK → ConfigEquipment)
├── 安装结构件编号
├── 电搭接面
├── 紧固件牌号、数量、归属团队
├── 设备托架型号
├── 托架来源（自制/外购）
├── 托架重量 (bracket_mass_kg)
├── 螺钉规格
├── 线搭接接口尺寸
├── 数模采用构型
├── 公差尺寸工程图（图片附件）
├── 是否已签字确认
└── 确认日期
```

### A.3 DO-160 记录 — 一对多关系

```
DO160Record
├── id (PK)
├── equipment_id (FK → ConfigEquipment)
├── 测试类别 (ENUM: 温度/振动/湿度/高度/电磁/...约25类)
├── 设计等级
├── 鉴定等级
├── 鉴定状态 (符合/不符合/待确认)
├── 鉴定报告编号
└── 备注
```

### A.4 实物管理记录 — 一对一关系

```
PhysicalAssetRecord
├── id (PK)
├── equipment_id (FK → ConfigEquipment, UNIQUE)
├── procurement_status (生产/测试/运输/到货)
├── expected_arrival_date
├── actual_arrival_date
├── micd_confirmed (bool)
├── structure_ready (bool, 是否已开口)
├── installation_ready (bool, 是否达到安装要求)
├── ready_for_aircraft (bool, 达到装机要求)
├── planned_install_date
└── actual_install_date
```

### A.5 设备间约束关系 — 多对多关系

```
EquipmentConstraint
├── id (PK)
├── equipment_a_id (FK → ConfigEquipment)
├── equipment_b_id (FK → ConfigEquipment)
├── constraint_type (安装位置依赖/空间冲突/...)
└── description
```
